# 第 1 週診斷題庫：建置、部署、CI/CD

這個 repo 是 Croc-O-Bet 的複本，專門拿來練「辨識與分析問題」。
每一題都在獨立的分支上，分支裡的程式碼已經被動過手腳，模擬一個真實團隊會遇到的狀況。

## 題目

| 題號 | 分支 | 症狀 |
|---|---|---|
| 01 | `drill/w1-01` | 上線新版後，一半使用者還是看到舊版，部分人開發者工具一打開就報錯 |
| 02 | `drill/w1-02` | 同一份程式碼，本機正常、staging 正常、production 打錯 API |
| 03 | `drill/w1-03` | PR preview 網址看得到介面，但鱷魚永遠不出現，本機完全正常 |
| 04 | `drill/w1-04` | 一個小 PR 讓 bundle 大了好幾倍，CI 的 size check 紅了 |
| 05 | `drill/w1-05` | E2E 測試本機 5 次全過，CI 10 次掛 3 次，而且錯誤訊息不一樣 |

## 流程，每題一樣

```bash
git switch drill/w1-01
```

1. 先讀 `drills/week1/01-*.md`，只有症狀和證據，沒有答案。
2. 計時 20 分鐘。不要先開程式碼，先憑症狀寫下假設，再決定要看哪些檔案去驗證。
3. 在 `drills/week1/answers/01.md` 依照下面的模板作答。超過 20 分鐘就停筆，寫到哪算到哪，這是在練面試的節奏。
4. 作答完 commit 在該分支，然後把答案貼給 Claude，Claude 會給你真實根因和你推理的落差。
5. 最後寫一份「給 AI 的修復 spec」，Claude 執行，你負責驗證結果是不是真的修好。

## 作答模板

```markdown
## 假設（依可能性排序，最多三個）
1.
2.
3.

## 我要查的證據（具體到檔案或工具面板）
-

## 我認為的根因
（看完證據後寫，一兩句話）

## 修法與取捨
- 修法：
- 副作用或代價：
- 不這樣修的替代方案：

## 給 AI 的修復 spec
（要具體到 AI 不用猜：改哪個檔、預期行為、怎麼驗證算修好）
```

## 規則

- `.drill-answers/` 是解答，已經 gitignore，自己不要看。
- 證據裡有雜訊是故意的，真實的 log 本來就有紅鯡魚。
- 每題都可以 `npm run build`、`npm run dev` 去重現，但先推理再動手。
